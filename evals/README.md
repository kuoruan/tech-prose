# 技能行为评测

本目录保存案例，具体运行状态与结果另行记录；不能据此判断模型效果或触发率。`tests/` 验证两个检查器，不验证模型能否正确执行技能。这里的案例用于补上验证缺口，不代表已经发现技能失败。

案例与输入集中在 [cases.md](cases.md)。这是手动评测套件，不新增运行依赖、不接入 CI。先在一个主要使用环境建立基线，再决定是否扩展。

## 分开测触发与执行

- **触发测试**：在目标宿主的真实新会话里，只提供案例请求及输入，不点名技能、不显式加载。观察宿主是否提供了技能、模型是否读取或调用了它。宿主若自动注入全文，应记录这一机制，不把它与按需读取混为一谈。没有可观察的加载证据时记为“不可判定”，不凭回答风格猜测。让子代理选择是否读文件不能代替真实宿主触发测试。
- **执行测试**：提供完整的待测技能目录（`SKILL.md`、`references/`、`scripts/`），保留相对路径，明确入口 `skills/tech-prose/SKILL.md` 并要求按技能处理案例。记录实际可读取的技能目录位置，允许模型按需读取参考文件，不要只粘贴入口正文。这测规则执行，不测自然触发。

两类结果分别记录，不合成一个“总分”。短请求未触发可能与宿主加载机制有关，记录现象，不自动归因于 description。

## 准备隔离环境

1. 固定宿主及版本、模型及版本或标识、工具、权限、语言和输入，记录待测技能的提交与未提交差异。不要在开发技能的长会话里运行案例。
2. 每个案例、每个对照组使用独立新会话和干净的临时工作区；任务工作区只放该例输入。技能目录在工作区之外只读提供；当前技能组与旧版本组都要能读到各自的完整技能目录，无技能组不可访问它们。不要把案例的判据、其他案例或评测者讨论提供给被测模型。
3. 执行对照可选“当前技能／无技能”或“当前技能／旧版本”。无技能组须使用没有自动加载 tech-prose 的独立配置，检查项目与全局技能、宿主指令、其他写作技能和继承上下文。不要为隔离而删除日常环境的技能。
4. 同一对照保持模型、工具与权限一致。无法排除额外指令或已安装技能污染时，记录限制，不声称有可靠的 A/B 结果。触发测试仅在提供目标技能的宿主配置中进行。
5. 运行前保存输入文件及文件清单，运行后比较内容与清单，检查有无增删文件；保留原始回答及可获得的工具轨迹。只读案例也保留与其他组相同的写入权限，才能观察是否擅自编辑。

案例输入中的命令仅为文本，不需要执行。不要给评测环境生产凭据；禁止访问生产系统或执行有外部副作用的命令。若需另行测试命令可执行性，先明确环境、权限与副作用，不与文字评测混在一起。

## 运行与判定

先跑执行案例，再单独跑触发请求。将各例“请求”里的文件名按“输入”建立为文件，只把请求和对应输入交给模型；无需输入的起草案例直接使用请求。显式加载仅用于执行组，不用于触发组。

每例逐项判定，不设唯一参考改写：

- **可机械核对的契约**：是否修改文件、是否增删文件、保护片段是否逐字保留、标题及顺序是否改变。可用文件差异或现有脚本辅助，脚本 PASS 不等于语义保真。
- **需人工核对的语义**：对象与数值是否对应，条件、否定、例外、不确定性和规范强度是否保留，有没有发明事实或恢复能力。
- **需人工评审的写作质量**：是否更清楚、是否解决具体缺陷、是否产生无收益改动。比较版本时先隐藏版本标签，再看输出。

不以禁词数、改动量、相似度或字数减少作为质量分。没有明显收益可以判“无差异”，不要强行选赢家。小样本仅供发现问题，不证明跨模型或跨宿主有效；遇到波动时重复运行并记录次数，不挑最好的一次。

## 结果记录

将运行结果保存在临时工作区，不覆盖案例中的“未运行”状态。每次至少记录：

- 运行日期、宿主与模型标识、工具和权限、技能版本及差异、对照方式、隔离检查结果。
- 案例 ID、运行序号、原始回答、文件差异、工具轨迹；无法取得的证据注明缺失。
- 每个判据的“通过／失败／不可判定”和证据。未运行单独标记，不能算通过。
- 人工质量判断、理由、耗时及可获得的 token 用量；不可获得的不估算。

若不能证明基线隔离，只保留单组执行观察，不报告技能带来的提升。判据全部满足也只说明这些案例下未发现问题，不说明所有输入都可靠。

## 可选：复杂文档冷读

需要时用独立会话，仅提供最终正文和读者任务问题，要求答案指出正文依据，并区分正文陈述与模型推断。找不到依据就说明无法回答，避免模型用常识补全掩盖文档缺口。冷读不是默认步骤，不替代真实用户验证。
