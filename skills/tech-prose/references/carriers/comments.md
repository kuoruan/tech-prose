# 代码注释与 docstring

两类注释的目标不同，规则也不同。混用是常见错误：把面向调用者的契约写成随手备忘，或把实现细节写进公开 API。

## 两类注释各写什么

| | 文档注释（docstring，导出/公开 API） | 实现注释（函数体内） |
|---|---|---|
| 面向 | 调用者，可能看不到实现 | 下一个改这段代码的人 |
| 必须写清 | 行为、返回值、异常、前置条件、副作用、并发约束、边界输入、弃用与替代方案 | 非显然的原因、机制、约束、workaround 及其原因、跨文件耦合 |
| 形式 | 必须是完整句；以符号名还是动词开头、用不用 `reports whether` 这类措辞，按项目与语言惯例 | 不强制成句，但要能读懂 |
| 不写 | 当前实现用的算法、内部数据结构、临时路径 | 代码已经说清的东西 |

“只写 why 不写 what”只适用于实现注释；文档注释的 what 正是调用者需要的。

行内注释里出现调用者契约（单位、阻塞行为、异常条件）时，项目惯例把它放在实现注释里就跟随项目；否则报告给用户，由用户决定是否提升为 docstring。提升会改变代码文本与 `__doc__`，不在润色授权范围内。必要信息优先于行数：需要两句话就说两句，不要为了压成一行而删掉契约内容。

## 零信息的文档注释

每条 docstring 和每个 `Args`/`Returns` 条目都要能通过这个测试：除了名字和类型之外，它告诉读者什么？答不出来就**删掉整条**。保留成只重述参数名的最短形式，同样算噪声。

`Args` 不要求逐项齐全：缺几个条目不是缺陷，留零信息条目才是。

零信息的典型形态：

```python
def build_request_config(base_url, timeout=10, retries=3):
    """Build the request config object for the request.

    Args:
        base_url: The base URL.
        timeout: The timeout.
        retries: The retries.
    """
```

整段可以删除：函数名已经说明 build request config，参数名已经说明 base_url。真正值得保留的只有名字未交代的内容，例如单位（`timeout` 是秒还是毫秒）、取值范围、默认值的来由。

改写后仍保留全部零信息条目，等同于没有修改。精简注释任务里，先处理这种冗余，再处理行内注释。

实现是占位或缺失时（`pass`、`TODO`、空函数体），注释可能是唯一的意图说明。这时保留它，把无法从代码核实的部分列为待核查，不按零信息删除。

## 只写有依据的

给 docstring 补上没有依据的契约，是最容易发生的一类错误：补写的内容在语法与风格上都成立，评审时难以察觉。常见形态是凭空写出 `:raises TimeoutError:`、关闭后抛错、重复释放报错。

以下注释特有的契约项也要有依据，依据范围同 `SKILL.md` 保护边界第 3 条（用户材料、已核实的源码或文档）：

- 会抛什么异常类型
- 关闭/失效后对象还能不能用
- 重复操作（重复释放、重复注册）会不会报错
- 超时后是取消还是继续
- 并发是否安全、哪些方法例外
- 边界值（0、负数、超上限）的行为
- 是否影响已检出的资源

需要这些信息时，把缺口列出来问；注释里只写能核实的内容。名字存在不等于语义已知：`PoolClosed` 只声明为 `RuntimeError` 子类，不代表“关闭后所有操作都抛它”。

## 改动边界

- **只改注释文本，代码字节不变。** 不重命名、不提取变量、不合并声明、不调整语句结构。“精简注释”不等于重构：`config = {...}; return config` 不能合并成 `return {...}`。
- 公开 API 的 docstring 可能被测试、文档生成、类型检查工具依赖。改措辞时确认语义没变；不确定就只报告，不改。
- 保留既有标记：`TODO:`、`FIXME:`、`HACK:`、`NOTE:`、`Deprecated:`、`//go:generate` 这类指令注释、ADR 编号、issue 链接。
- 注释语言跟周围文件走，不单独切换。周围没有先例时问。

## 实现注释的内容

- 非显然的 why：`// provider webhook 可能早于自己的 DB 提交`。
- workaround 及其原因，能带链接就带：`// 绕过 nodejs/node#1234`。
- 顺序或依赖约束：`// 顺序不能改：鉴权必须在限流之前`。
- 跨文件耦合：`// 与 schema.prisma 保持一致`。
- 指向更深上下文：ADR 路径、URL、issue 号。

## 实现注释与其他载体的分工

以下内容不写进实现注释，它们属于别的载体。

- 代码已经说清的动作（`// 遍历用户`）。
- 复述签名的 docstring（`# 构建请求配置对象` 对应 `build_request_config()`）。
- 变更史（`// 改成 30 秒了`、`// 之前用 JWT`）。历史属于提交信息和 PR。
- 装饰性分隔条（`// ===== Helpers =====`）。
- 已注释掉的代码：这类信息由版本控制承担。

## 交付前

- 注释与 docstring 之外，代码文本是否与原文一致；AST 只作辅助核对，不能替代文本比对。
- 是否补了原文没有的契约。
- 是否删掉了限制、异常条件、并发说明或弃用提示。
