# 界面文案

范围：产品界面里的操作文案（按钮、链接、菜单、标签页、字段标签、帮助文本、placeholder、tooltip、toast、横幅、空状态、加载状态、确认框、权限请求、设置项）。CLI 的帮助、报错与进度文案见 `cli-output.md`，帮助文档的章节结构见 `documentation.md`。营销页面、落地页、长文案，以及交互结构、控件类型与体验设计均不在本文范围内。

边界：本文只判断文案怎么写，不判断界面该怎么设计。控件位置与类型、确认流程、状态流转、撤销与重试能力、分页、图标与可读名称、国际化实现属于产品既有设计。缺什么列建议，不改功能、不编参数。排列顺序同理：起草可建议顺序，改写现有文案不调整顺序。

判据：用户能否一眼读出“发生了什么、要做什么、接下来会怎样”。读不懂时先怀疑这句话承担了不该由它承担的信息，而不是加字。

## 元素规则

元素是举例，不穷尽；同类元素按同一判据处理。形状里的 `<>` 是占位，实际标点按语言规则。

| 元素 | 规则 | 形状 |
|---|---|---|
| 按钮 | 动词开头，说清结果；是动作不是反应 | `<动词> <对象>`：`保存更改`、`删除项目` |
| 链接 | 写清目标，不用“点击这里”“详情” | `导出 CSV`、`查看计费记录` |
| 菜单项 / 标签页 | 名词短语，与页面标题用同一套词 | `账单设置` |
| 字段标签 | 名词短语，句子式大小写；单位与范围写明，不让读者去别处拼凑 | `超时（秒）` |
| placeholder | 写能直接照填的示例值；不写指令句（`请输入…`） | `name@example.com` |
| 帮助文本 | 讲格式、范围与为什么要填 | `用于接收告警，可随时修改` |
| tooltip | 一句话，解释标签没说的部分或为什么不可用 | `<做什么 / 为什么禁用>` |
| toast | 陈述刚发生的结果，过去时；不复述按钮 | `<对象> <已完成动作>。` |
| 横幅 | 说明影响与恢复动作 | `<影响>。<恢复动作>。` |
| 空状态 | 说清这里该有什么；区分“还没有”与“筛选后没有”；产品已有下一步动作时写明 | `<缺什么>。<动作>。` |
| 加载状态 | 说明在做什么；产品已有完成提示时，结果写在那里 | `正在同步 12 个文件…` |
| 字段级错误 | 点名具体值与要求 | `至少 8 位，当前 6 位。` |
| 页面级错误 | 发生了什么 + 为什么（已知时）+ 怎么修 + 详情在哪 | `<现象>。<原因>。<动作>。` |
| 确认框 | 标题与按钮都点名对象与动作；正文给后果 | `删除这个项目？` |
| 破坏性确认 | 点名对象、数量与可恢复性 | `<动作> “<对象>”？<数量>。<可恢复性>。` |
| 权限请求 | 说明用来做什么、拒绝后失去什么 | `读取日历以生成日程；拒绝后只能手动添加。` |
| 禁用态 | 说明为什么不可用、怎样才能可用 | `需先选择工作区` |
| 设置项 | 标签说明这一项是什么；已有帮助文本时，取值的影响写在那里 | `自动续期` |

## 同一操作前后一致

- 同一操作的按钮、进行中、完成、失败，动词与对象要对得上；`正在删除…` 配 `移除` 按钮，读者会以为这是两个操作。
- 成功提示不复述按钮文字：按钮已经说了要做什么，结果说的是发生了什么。
- 失败信息点名具体字段或对象，并给出产品确实支持的下一步：`邮箱格式不正确，请填写 name@example.com`。`请重试` 只在产品行为已知时写，否则留缺口。
- 能撤销或能重试的地方写出来；做不到就说明原因（不可逆、需联系支持），不写空泛的“如有问题请反馈”。
- `删除` 与 `移除` 是否同一操作由产品定义，不因文字相近就统一；确认前保留原词。

## 错误信息

按顺序说三件事：发生了什么、为什么（已知时）、怎么修。只写发生与修法两句时，先发生、后修法。点名具体值、格式、限制或冲突状态。CLI 报错同样按这一节判断。

- 不写不点名对象的句子：`出错了`、`操作失败`、`系统异常`。错在字段就点名字段，错在服务就点名服务。
- 不责怪用户：避免“非法”“无效”“你的输入有误”，改成要求本身。错误必须在文本里说清，颜色和图标只是辅助；不用感叹号。
- 知道修正方式时给出：正确格式、可选值、下一步。给出前先确认产品确实支持这个修法。
- 产品已有错误码、请求 ID 或 trace ID 时，按既有格式放在正文之后；没有就不编一个。
- 同一块里的重复错误合并成一条；是否显示数量按产品已有行为，不新造运行期聚合计数。
- 涉及金额、不可逆操作或法律后果时，写清是否已生效、能否撤回，依据是产品已有能力。
- `抱歉`、`请` 只在用户确实被耽误、且产品既有文案如此时使用，不当填充。

错误文案属于代码文本：需要插入变量时列出需要的值让调用方确认，不自行往调用里加参数。

## 破坏性确认的文案

文案交代四件事：对象（同名时给路径、ID 或域名）、范围与数量、后果、可恢复性。只写产品已有的事实，缺的留占位。

- 可恢复就写可恢复；可恢复性未知时留占位，不写“删除后不可恢复”。
- 产品已有确认、预览或撤销能力时，文案把这个能力说清；没有就只写后果，不加承诺。

## 变量、占位与本地化

- 改写现有代码时，保留原有占位符、类型、顺序与转义：`%s` 不会因为“更好读”变成命名模板。新起草的文案才建议命名占位 `{count}`、`{project_name}`、`<n>`。
- 不拼接句子片段：语序、量词与格会变。已有模板长度不够时，提出整句模板的建议，不直接拆词。
- 复数、量词、日期与数字格式按目标语言的既有惯例处理；产品已有本地化机制时跟随，不另造写法。
- 缩写首次出现给全称；面向本地化或第二语言读者时避免缩写。
- 不写装饰性的时效内容（节日、当年），用户会在很久以后看到它；真实期限、有效期照原样保留。

## 可扫读

- 链接文字说明目标，不写“点击这里”“详情”。
- 一次只说一件事：标题给结论，正文补原因与做法。删掉铺垫（`在此页面中，您可以…`）。
- 标点：按钮、标签、菜单项、toast 不加句号；tooltip、错误与对话框正文是完整句就加句号。
- 不用纯符号代替文字结论。

## 需求缺少产品事实时

破坏性确认需要知道删除数量与是否可恢复，错误信息需要知道发生了什么。需求中常缺这些信息。

- **写占位**：`该项目下的所有 <n> 个任务会一并删除。` `<n>` 留到拿到真实数量再填。
- **功能缺失不证明最终结果**：可恢复性与补救步骤要有产品事实依据。产品没有回收站，不代表不能通过支持渠道或备份恢复。事实未知时留占位，不要写成 `This cannot be undone` 或“删除后不可恢复”。
- **一个占位一个问题**：按占位出现的顺序问，每个都指明属于哪个元素。
- **带占位的行是草稿**：交付时标注该行尚未达到上线条件。
- **同一块里不缺事实的元素照常交付**：只有缺事实的那几条留占位。

占位留在草案里；写进可发布文案或代码之前，先拿到答案。

## 改写已有文案

- 原文里的数字、名称、具体主张原样保留。把语气改坏，代价远小于把事实改错。
- 做两件事：删除没有信息的部分；补上这条文案的规则需要的、且输入里确实有的事实。
- 原文可用时说明无需修改；每处改动都要指向具体缺陷。

## 中英文

结构规则跨语言成立：动词开头的按钮、先说现象再说修法的错误、点名后果的确认。

中文界面文案的常见问题（箭头后是缺的那一块）：

- `确认删除吗？` → 没有对象、没有后果、没有可恢复性。
- `操作成功` → 系统的视角，用户关心结果状态。
- `删除成功！` → 删除感叹号。
- `暂无数据` → 没说这里该有什么，也没给下一步。
- `确定`/`取消` 作为危险操作的两个按钮 → 确认按钮应重述动作，如 `删除项目`。
- 动态内容（项目名、用户名）用全角引号 `“项目名”` 隔开，避免与句式粘连；产品已有 `「」` 先例时跟随。

英文界面文案的额外要点：

- 句子式大小写：`Delete project`、`Save changes`，不是 `Delete Project`。引用界面上全大写或大小写不一致的标签时，统一写成句子式大小写。
- 确认是同一个动作后全程用一个动词，`Delete` 与 `Remove` 不混用；两个动词对应不同后果时保留。
- 确认框标题问“做什么”（`Delete this project?`），不是 `Are you sure?`。
- 新起草时，变量与数量按命名占位写（见“变量、占位与本地化”）：`{project_name}`、`<n>`；改写已有文案保留原有占位格式。
- 动态内容用半角引号隔开：`Delete "Project name"?`；引号与内容之间不加空格，其余标点按 `references/languages/en.md` 的规则。
- 缩写与第二人称可用（`can't`、`you're`）；`please` 等客套语按产品既有文案风格取舍，没有先例时省略。

## 范围之外

- 交互结构、控件类型、状态流转、视觉与体验设计。
- 错误码命名、i18n 工程实现（字符串提取、复数引擎）、日志级别设计。
- 合规文案（条款、同意、价格免责）：表层问题可以修，涉及含义的改动交给人确认。
- 品牌规范优先于这里的默认规则；冲突时按品牌规范，然后回到这里补它没覆盖的部分。
