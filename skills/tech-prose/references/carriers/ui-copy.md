# 界面文案

范围：产品界面里的操作文案（按钮、错误、空状态、确认框、placeholder、tooltip、toast、字段标签），以及 CLI 的运行期输出（报错、告警、进度）。营销页面、落地页、长文案不在本 skill 范围内；视觉与交互不在本文范围内。

语体：简明、直接、尊重用户；说清动作、结果、后果与恢复路径，语气平实，就事论事。

## 元素规则

| 元素 | 规则 | 形状 |
|---|---|---|
| 按钮 / 链接 | 动词开头，点明结果。句子式大小写。用能说清结果的表达作标签 | `<动词> <对象>`：`保存更改`、`删除项目` |
| 错误信息 | 先说发生了什么，再说怎么修；原因已知时补一句。语气中性 | `<发生了什么>。<怎么修>。` |
| 空状态 | 说清这里该有什么，再给一个填充它的动作 | `<缺什么>。<动作>。` + 一个按钮 |
| 破坏性确认 | 点名具体后果：删除什么、数量多少、是否可恢复 | `<动作> “<对象>”？<后果>。<可恢复性>。` |
| placeholder | 给出一个示例值；字段名由持久标签承担 | 短的示例值 |
| tooltip | 一句话。说明控件做什么，或为何不可用；重点是标签未能涵盖的信息 | `<做什么 / 为什么禁用>` |
| toast | 陈述结果，过去时 | `<对象> <已完成动作>。` |
| 字段标签 | 句子式大小写，说明字段内容 | 短名词短语 |

## 状态一致

按实际存在的状态核对，不要求每个动作都配四种提示：

- 同一操作的按钮、进行中、完成、失败，动词与对象要对得上；`正在删除…` 配 `移除` 按钮，读者会以为这是两个操作。
- 成功提示不复述按钮文字：按钮已经说了要做什么，结果说的是发生了什么。
- 失败信息点名具体字段或对象，并给出产品确实支持的下一步：`邮箱格式不正确，请填写 name@example.com`。`请重试` 这类动作只在产品行为已知时写，否则留缺口。
- `删除`与`移除`是否同一操作由产品定义，不因文字相近就统一；确认前保留原词。

## 错误信息

按顺序说三件事：发生了什么、为什么（已知时）、怎么修。只写发生与修法两句时，先发生、后修法。点名具体值、格式、限制或冲突状态。

语气中性：不道歉、不责怪、不用感叹号。

错误文案属于代码文本：保持函数签名与参数不变；需要插入变量时列出需要的值让调用方确认，不自行往调用里加参数。

## 需求缺少产品事实时

破坏性确认需要知道删除数量与是否可恢复，错误信息需要知道发生了什么。需求中常缺这些信息。

- **写占位**：`该项目下的所有 <n> 个任务会一并删除。` `<n>` 留到拿到真实数量再填。
- **功能缺失不证明最终结果**：可恢复性与补救步骤要有产品事实依据：产品没有回收站，不代表不能通过支持渠道或备份恢复。事实未知时留占位，不要写成 `This cannot be undone` 或“删除后不可恢复”。
- **一个占位一个问题**：按占位出现的顺序问，每个都指明属于哪个元素。
- **带占位的行是草稿**：交付时标注该行尚未达到上线条件。
- **同一块里不缺事实的元素照常交付**：只有缺事实的那几条留占位。

占位留在草案里；写进可发布文案或代码之前，先拿到答案。

## 改写已有文案

- 原文里的数字、名称、具体主张原样保留。把语气改坏，代价远小于把事实改错。
- 做两件事：删除没有信息的部分；补上这条文案的规则需要的、且输入里确实有的事实。
- 原文可用时说明无需修改；每处改动都要指向具体缺陷。

## 中英文

结构规则跨语言成立：动词开头的按钮、先说现象再说修法的错误、点名后果的确认。

中文界面文案的常见问题（括号里是缺的那一块）：

- `确认删除吗？` → 没有对象、没有后果、没有可恢复性。
- `操作成功` → 系统的视角，用户关心结果状态。
- `删除成功！` → 删除感叹号。
- `暂无数据` → 没说这里该有什么，也没给下一步。
- `确定`/`取消` 作为危险操作的两个按钮 → 右边按钮应重述动作，如 `删除项目`。
- 动态内容（项目名、用户名）用全角引号 `“项目名”` 隔开，避免与句式粘连；产品已有 `「」` 先例时跟随。这类内容可能超长、含标点或空格，截断交给 CSS。

英文界面文案的额外要点：

- 句子式大小写：`Delete project`、`Save changes`，不是 `Delete Project`。
- 按钮、字段标签、toast 不加句末句号；确认框正文这类完整句加。
- 确认是同一个动作后全程用一个动词，`Delete` 与 `Remove` 不混用；两个动词对应不同后果时保留。
- 确认框标题问“做什么”：`Delete this project?`，不是 `Are you sure?`。
- 变量与数量用命名占位：`{project_name}`、`<n>`。
- 动态内容用半角引号隔开：`Delete "Project name"?`；引号与内容之间不加空格，其余标点按 `references/languages/en.md` 的规则。
- 缩写与第二人称可用（`can't`、`you're`）；`please` 等客套语按产品既有文案风格取舍，没有先例时省略。

## 范围之外

- 交互结构、控件类型、视觉设计。
- 合规文案（条款、同意、价格免责）：表层问题可以修，涉及含义的改动交给人确认。
- 品牌规范优先于这里的默认规则；冲突时按品牌规范，然后回到这里补它没覆盖的部分。
