# 技术文字改写

处理对象是技术文字：给读者看的文档、给下一个改代码的人看的注释、给用户看的界面文案、给 AI 执行的指令文件。

**目标**：准确、自然、易找、可行动。去 AI 腔是辅助手段，不能凌驾于这四项之上。

**默认范围。** 优化措辞、术语、语气与标点。可以拆分长句、把讲了两件事的段落拆开、合并重复、删掉不含信息的表达。这些局部调整不改变章节与顺序，也不改变技术信息之间的关系。不主动新增章节、搬移内容、拆分文件，也不改动标题层级与编号。调整章节归属或顺序须用户明确要求。“太长”“精简”“易读”只授权措辞层面，结构问题另列建议。

## 先定请求

用户的请求决定动作。只问看法就只读，要求改才编辑。

- **只问“看看/检查一下”** → `review`（审阅）：只读，列问题和依据，不改文件。
- **有原文且要求改**（“优化”“润色”“精简”“改严谨”）→ `revise`（改写）：给改写结果。
- **没有原文，要求写** → `write`（起草）：给正文。

输出形态跟着动作走：

- `review`：`路径:行号` + 问题 + 依据 + 建议。只有粘贴或口述的文字时，用原句定位。
- `revise`：改写后的文字。影响本次修改但材料不足以确认的信息，列为缺口；没有此类缺口则省略。改动说明只写读者需要的部分——非显然的取舍、可能被反对的改动、缺口清单。明显的修正不必逐条解释。不是方案文档。
- `write`：正文，附未解决的缺口。

改前/改后对照只在逐条比对界面文案、错误信息这类短文案时用。

`revise` 与 `write` 的交付物只写文案本身和真正的缺口；`review` 的交付物就是问题清单。读者不需要看到工具的词汇——`revise`、`review`、`write`、自检编号都属于内部说法。

交付语言：改写正文跟随原文语言；改动说明与缺口清单跟随用户的提问语言。

## 改动前的三个判断

三个判断互相独立，只有第三条命中时整体退出。

**一、哪些片段一律不动。** 引用、专名、用户或项目规范要求原样保留的标题、代码块、路径、命令、链接目标。它们原样出现，其余部分照常改。用户明确要求调整结构时，可更新因移动而失效的内部引用，核实目标与含义后改动；其他路径、命令与标识符仍保持原样。

**二、这个缺陷值不值得改。** 单条弱信号先保留。同一段里多条一起出现才构成证据；单条已经明确损害准确性或可读性时直接改。原文已经合格时，回复“无需修改”是合法结果。反过来，写得好的段落允许小幅修改，前提是每处都能指出具体缺陷（如裸 `429` 补成 `a 429 response`，避免读成数量）。“改动越小越好”不是判据。

**三、这个请求是否超出范围。** 用户真正要的是翻译、重构、换个技术方案时退出，说明这不在范围内。

## 优先级与保护边界

事实与契约 > 合规与安全要求 > 项目术语、品牌与载体惯例 > 用户明确指定的语体 > 可读性 > 去 AI 化偏好。

用户当次给的写作样本或品牌规范，优先于本表“项目术语与载体惯例”及以下的各项；事实、契约与合规安全不受影响。

适用范围：下面六条针对的是不可逆、或表面完全合理却难以察觉的错误。任一条被违反，本次交付需要重做。

1. **事实与代码不动。** 数字、版本、限额、标识符、路径、参数默认值必须与原文完全一致。结构授权后内部链接的处理见判断一。**代码本身不改**——不重命名、不合并语句、不调整结构、不动公共 API 契约。精简注释不等于重构。
2. **不擅自换语言。** 中英混排的文档，优化英文段落不等于把它译成中文，反之亦然。要改语言先问。
3. **不发明契约。** docstring 里的契约项，例如抛什么异常、并发下什么行为、边界值如何处理、关闭后是否可再用，都要有依据。依据来自用户给出的材料、已核实的源码或文档。原文注释没写但代码里确实 `raise ValueError`，可以补。只有推断，不补。这类补写在语法与风格上都成立，评审时难以察觉。新增引用同理：先核实目标存在且支持所述内容。指向不存在或内容不符的文档、章节、URL 都是凭空断言。
4. **缺事实就标出缺口。** 已经存在的文档和源码：保留原文，把待核查项写进报告。新写的 UI 草案可以用命名占位（如 `<n>`）并提问，占位留在草案里，不进入可发布文案或代码。
5. **删信息和编信息同等严重。** 限制、前提、例外、回滚方式、失败路径，删掉一句就可能让读者做出错误判断。
6. **不确定就是不确定。** `可能是 A`、`尚未验证`、`需要压测确认`、`usually`、`advisory` 这类表述承载真实信息，照原样保留其中的不确定性。`必须/建议/允许`、`MUST/SHOULD/MAY` 的强度差别也原样保留。

## 按需加载

只读命中的文件。一个任务可能同时命中多个：载体决定写什么，语言决定怎么写。载体里已经写明的语言交叉规则优先于语言文件的默认值。

**语言**

- 中文，或中英混排：`references/languages/zh.md`；有整段英文时同时读 `references/languages/en.md`。
- 英文：`references/languages/en.md`。

**载体**

- 文档、README、设计说明、API 参考、release notes：`references/carriers/documentation.md`。
- 提交信息、PR 描述：`references/carriers/commit.md`。
- 代码注释或 docstring：`references/carriers/comments.md`。
- 界面元素文案（按钮、链接、字段标签、空状态、加载、错误、确认框、权限请求）：`references/carriers/ui-copy.md`。
- CLI 的帮助、报错、进度与结果提示：`references/carriers/cli-output.md`；需要组织帮助文档章节时同时读 `references/carriers/documentation.md`。
- AGENTS.md、CLAUDE.md、`.cursorrules`、技能文件 SKILL.md 或同类 agent 指令文件：`references/carriers/ai-instructions.md`。

**结构调整**（审查结构或明确要求重组时）

- 审查文档结构，或用户明确要求重排章节、调整目录、改动标题层级或编号、拆分或合并文档、重组 README：`references/tasks/structure.md`。只审查时只报告结构问题，改动文件仍须用户明确要求重组。

## 共用表达原则

### 语体

按对象选一档：技术文档与代码注释要准确、客观、专业——用行业惯用词，直接陈述事实，证据不足就如实标注。界面文案与 CLI 输出要简明、直接、尊重用户，说清动作、结果、后果与恢复路径。

清晰易读不等于口语化，严谨也不等于公文腔。判据是能否脱离日常语境读懂：俚语、网络梗、语气词、动作含义不明的表达属于口语化；`本页面所述之` 属于公文腔。常见缩写与第二人称都不属于口语化。两端的例子见语言文件。

### 句子与语义关系

- 一句话承载一件事。需要回读才懂时拆开；拆开后仍要看得出条件的作用范围与它对应的结果。
- **精简套壳表达**：`进行优化`→`优化`，`作出判断`→`判断`，`perform validation`→`validate`。改的前提是删去后原意、规范强度与语气都不变；变了的就不是套壳，是内容。名词化看它是否只增加字数，被动看它有没有遮住读者需要的主体，两种分开判断，不凭句式判错。

改措辞最容易碰坏的是句子之间的关系，不是词。动笔前确认这几件事还在原处：

- **谁执行**。动作主体影响理解时写明主体。材料没给就留缺口，不猜；主动或被动按表达需要选，被动本身不是缺陷。
- **指代**。`它`、`该`、`这个` 可能指向多个对象时澄清，重说名词或点名具体对象。
- **条件的范围**。`只有在 X 时才能 Y` 要能看出它管到哪一步；`或` 与 `且` 不互换——`A 或 B 时` 不是两个条件同时满足。
- **因果**。`因为`、`所以`、`导致` 必须是真的因果，不能把并列关系写成因果。
- **否定的范围**。`并非全部失败` 与 `没有失败` 是两件事。改写要让读者一次读清否定管到哪一部分；原文的否定范围与语气保留，`不是不需要校验` 只有在需要回读时才改写。
- **列举是否穷尽**。`以下原因`、`包括`、`例如` 各自不同：原文是非穷尽，就不要改成 `三个原因`。

### 段落、分点与换行

- 一段一件事。过长、或在一段里换了话题，就拆开或列成分点。
- 有先后顺序用编号，否则用项目符号。不为了排版对称造单项列表；单步骤流程按既有惯例。
- 列表的引导与条目关系要清楚，标题、短语或完整句都可以。`支持以下格式：` 后另起列表列出 `JSON`、`YAML` 是正常写法，不必补成完整句。
- 各条角色相同时尽量平行：都用动词开头，或都用名词短语；角色不同的条目不为形式硬凑。
- 标点跟着内容：整条是片段、纯代码或纯链接，不加句号；含动词的完整句加。
- 同类条目用列表；要横向比较多个属性时用表格，条目只是各自带几个属性时不必改成表格。
- 换行看它会不会改变渲染或 diff：一行一句便于查看与修改；渲染层长度不影响结果时，不按固定列宽硬折。载体有硬折约定时遵循该约定（提交正文见 `references/carriers/commit.md`）。

### 冗余与形式化表达

下列模式跨语言成立；中文用词与句式见 `references/languages/zh.md`，英文句式见 `references/languages/en.md`。

- **铺垫开场**：先说“随着 X 的发展”“在这个背景下”，再讲事实。删掉铺垫，第一句直接给事实。
- **“不是 X，而是 Y”**：对偶式对比（`This isn't just a cache — it's a contract`、`这不是缓存，而是契约`）。通常只需陈述 Y 本身。
- **排比三连**：三个例子若只是形式对称、内容重复，收成一个；各承载不同信息时保留。
- **一行式收尾**：只重复前文的总结、升华、或“这就是 X 的意义”。删除；补充了新内容的收尾保留。
- **加粗当装饰**：整句加粗、用加粗代替标题分层、给本来没有信息的内容加粗。词条式列表（`**指代**。……`）、参数表与定义列表里加粗的标签（`**Capacity:** 50,000`）属于结构：它们各是一条查找键。判据看加粗是不是在替代标题或强调，不看加粗本身。
- **空泛评价**：`强大`、`无缝`、`很明显`、`非常关键`。追问它到底指什么；能用指标、条件或后果替换就替换，没有依据才删。
- **伪造重要性**：把普通事实写成“不容忽视的问题”“关键转折”。按事实本身的量级陈述。

## 交付前自检

任一条答“是”，按对应小节处理，并遵守保护边界。`review` 只报告问题，不改文件；改写已有文字时，缺依据的内容保留原文并列为待核查项；`write` 缺依据时列缺口，不凭空补全。自检编号不进入交付物。

**正文质量检查**：`review`、`revise`、`write` 都查，针对正文自身。

1. 有铺垫或开场废话吗？
2. 有没有不含信息的对偶（“不是 X 而是 Y”）、机械排比三连、或装饰性强调？对偶本身不是缺陷，删掉对比不损失信息时才是。
3. 有没有缺依据、缺条件、也没有假设标记的强主张？
4. 有没有缺乏依据的技术细节（异常类型、并发保证、边界行为、计划与承诺）——原文、源码、用户材料都没有出处？有没有未经核实的引用——目标不存在，或内容与所述不符？
5. 有没有语体与对象不匹配的地方——技术文档写成聊天、界面文案写成公文？
6. 有没有把口语带进文档——俚语、梗、语气词、口头禅、动作含义不明的表达、感叹号？
7. 有没有不必要的公文腔？
8. 数字、版本、限额或规范要求有没有自相矛盾？
9. 有没有把尚未验证或只有推断依据的内容写成确定事实？
10. 根据已有材料，正文有没有漏掉必要的限制、前提、例外、失败路径或回滚说明？材料不足时列缺口，不猜测补全。

**改写保真检查**：只有 `revise` 查，逐条对比原文。

1. 数字、版本、限额、标识符、路径、参数默认值，以及 `必须/建议/允许`、`MUST/SHOULD/MAY` 这类规范措辞，有没有与原文不一致？内部链接的结构调整例外按保护边界处理。
2. 有没有把原文有依据的不确定性，改写成确定事实？
3. 有没有删掉限制、前提、例外或回滚说明？
4. 有没有指不出具体缺陷的改动？每处改动都要能指向一个真实存在的缺陷。
5. 有没有改动代码或公共 API 契约，或未经确认切换正文语言？

交付前如果原文是代码、或含 3 个及以上数字与标识符，可以跑 `scripts/check_rewrite.py <原文> <改写>`。它标出七类需人工复核的项：事实丢失、规范强度变化、不确定性变化、代码一致性、改动量、编造的名称、语言漂移。改动量只描述幅度，不参与退出码。**不作判决**；脚本开头 `KNOWN LIMITS` 一节列了它的误报类型。

自动检查的覆盖边界：规范强度只认 `MUST/SHOULD/MAY`（不区分大小写）与中文规范词，`is required to`、`can` 这类写法不计。中文数字只在带量词时计入，规范成阿拉伯数字会被报成丢失。代码一致性只覆盖 `.py` 文件，其他语言该项显示 `n/a`，不等于检查通过。
